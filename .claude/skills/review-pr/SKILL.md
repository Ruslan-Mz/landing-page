# Ревью pull request

Автор изменения плохо его ревьюирует: он читает то, что хотел написать, а не то, что написал. Скилл даёт изменению ревьюеров, которые начинают с нуля и смотрят каждый через свою линзу.

## 0. Условия

- **Свежая сессия.** Если эта сессия писала или правила код изменения — остановись и попроси владельца запустить скилл в новой.
- Аргументы: `$ARGUMENTS`. Первым идёт номер PR или `range <base>..<head>`. Если ничего нет — PR текущей ветки (`gh pr view --json number`).
- Владелец может добавить: `deep` (см. §2), `local` (не публиковать в GitHub, только отчёт здесь), `since <sha>` (смотреть только изменения после этого коммита).
- `range` — для изменений, закоммиченных без PR (например, прямо в `main`). В этом режиме ничего не публикуется в GitHub, отчёт только здесь, как при `local`.
- Ты дирижируешь. Сам код не ревьюируешь и ничего не исправляешь.

## 1. Подготовка

**С номером PR:**

1. `gh pr view <n> --json number,title,body,url,baseRefName,headRefName,headRefOid,additions,deletions,files,reviews`. `<owner>/<repo>` возьми из `url`.
2. Забери ветки по HTTPS, не через `origin` (SSH в сессиях Claude падает), с `gh` в роли разового помощника для учётных данных:
   `git -c credential.helper= -c credential.helper='!gh auth git-credential' fetch https://github.com/<owner>/<repo>.git +refs/heads/<baseRefName>:refs/remotes/review/<baseRefName> +refs/pull/<n>/head:refs/remotes/review/pr-<n>`
   Проверь, что `review/pr-<n>` указывает на `headRefOid`. Если нет — PR сдвинулся во время запуска: остановись.
3. Выложи PR в отдельный worktree **в scratchpad этой сессии**, чтобы рабочая копия владельца не трогалась: `git worktree add <scratchpad>/review/pr-<n> review/pr-<n>`. Если worktree от прошлого запуска остался (`git worktree list`), сначала убери его, как в §6.
4. Раунд: найди в ревью PR маркер `<!-- mozhaev-review round=… head=… -->`. Нет маркера — раунд 1.

**С `range <base>..<head>`:** оба конца — локальные ref или SHA. `git worktree add <scratchpad>/review/range-<короткий-sha-head> <head>`; base для диффа — `<base>`. Заголовок и описание — `git log --format='%s%n%n%b' <base>..<head>`. Раунд всегда 1.

5. **Зависимости и сборка — один раз, здесь, до запуска ревьюеров.** Ревьюеры работают в одном worktree параллельно, и одновременные сборки ломают друг друга, поэтому ставишь и собираешь только ты. Команды — в worktree, строго по очереди, с запоминанием кода выхода каждой:
   - `YARN_GLOBAL_FOLDER=<scratchpad>/yarn-global YARN_HTTPS_PROXY=$HTTPS_PROXY corepack yarn install --immutable` — кэш Yarn лежит в scratchpad, а не в домашней папке, и Yarn ходит через прокси песочницы. Упало на `ReadError: The server aborted pending request` — повтори ту же команду;
   - `corepack yarn build > <scratchpad>/review/<id>-build.log 2>&1`.

   `astro check` не запускается: `@astrojs/check` в проект не установлен.

   Красный `build` — не повод останавливаться: ревьюеры получают лог как есть. Не удалась установка — сборку не запускай, ревьюеры получают «проверка запуском пропущена: установка не прошла» и хвост лога.

   **Не ставь и не собирай**, если изменение трогает `package.json`, `yarn.lock`, `.yarnrc.yml` или `astro.config.mjs`: они исполняются при установке и сборке. Тогда ревьюеры получают «проверка запуском пропущена» с причиной, и та же строка идёт в отчёт.

   **Никогда не ставь зависимости в рабочей папке владельца**: там `node_modules` собраны под macOS.

## 2. Линзы

Файлы линз: `${CLAUDE_SKILL_DIR}/lenses/<имя>.md`.

| Линза | Когда запускать |
|---|---|
| `content` | всегда |
| `i18n-seo` | `src/lib/content.ts`, `src/lib/routes.ts`, `src/pages/`, `src/layouts/`, `src/components/{Seo,Schema,Topbar,ContactLinks,FacePage}.astro`, `astro.config.mjs`, `public/robots.txt`, `public/og/` |
| `build-ui` | любой `*.astro`, `src/styles/`, `src/lib/`, `src/assets/`, `public/`, `astro.config.mjs`, `package.json`, `yarn.lock`, `.yarnrc.yml`, `tsconfig.json`, `.claude/` |
| `deploy` | `.github/workflows/`, `netlify.toml`, `astro.config.mjs`, `src/pages/404.astro`, `public/robots.txt`, `DEPLOY-dual.md`, `.env.example`, `docs/adr/` с решениями о хостинге, DNS или сертификатах |

### Режимы

- **Обычный** (по умолчанию): два `pr-reviewer`:
  - **текст**: `content` + `i18n-seo`;
  - **код**: `build-ui` + `deploy`.

  Группа запускается, если таблица выбрала хотя бы одну её линзу; невыбранные линзы внутри группы не передаются. Проверка находок — самим ревьюером (шаг «попробуй опровергнуть» в его инструкции), без отдельного верификатора.

- **`deep`**: по одному `pr-reviewer` на каждую выбранную линзу и `review-verifier` на находки `High` и `Medium` (§4). Предложи его (и дождись ответа), если изменение трогает деплой, хостинг, DNS, `astro.config.mjs`, `routes.ts`, факты о Руслане в `content.ts` — или больше примерно 400 строк.

## 3. Ревью

Запусти ревьюеров выбранного режима **параллельно**. Каждому дай: путь к worktree, путь к основному репозиторию, base ref и команду диффа (`git -C <worktree> diff <base>...HEAD`), абсолютные пути его линз, список изменённых файлов, заголовок и описание, и `build` из §1.5 — путь к `dist/` и логу с кодом выхода либо «проверка запуском пропущена» с причиной. Напомни, что `install` и `build` в worktree ревьюер сам не запускает. Больше ничего: ни своих ожиданий, ни находок других ревьюеров.

С раунда 2 передай ещё прошлые находки и коммит, на котором они сделаны, и попроси (а) проверить, что каждая прошлая `High` и `Medium` действительно исправлена, (б) для каждой исправленной — соседние случаи того же дефекта (другой язык, другое лицо, другой хостинг), (в) ревьюировать только `git diff <прошлый head>..HEAD`. С `since <sha>` — то же, начиная с этого коммита.

Отчёт ревьюера — только то, что вернул его вызов Agent, с блоком json. Уведомление о завершении или сводка в пользовательском сообщении — сигнал статуса, а не отчёт. Прежде чем проверять находки, публиковать или убирать за собой, убедись, что ни один ревьюер не работает.

## 4. Проверка находок

1. Разбери блок json каждого ревьюера. Слей дубликаты: тот же файл, строки в пределах пяти, тот же дефект. Оставь более ясную формулировку и отметь обе линзы.
2. Только в `deep`: отправь каждую `High` и `Medium` в `review-verifier`, сгруппировав по линзам, параллельно, с тем же `build` из §1.5. Оставь `CONFIRMED`; `PLAUSIBLE` — только с проверенной серьёзностью `High` и с пометкой «не воспроизведено»; `REFUTED` убери.
3. Если выборочная проверка показывает, что утверждение в отчёте ложно, не выбрасывай его молча: получи отчёт от того агента заново.

## 5. Отчёт

Сначала находки с `decision: owner` под заголовком **Нужно ваше решение**, потом `author`. Каждая часть — таблица по серьёзности: серьёзность, класс, `path:line`, суть, вердикт (в обычном режиме — «самопроверка»). Потом сценарий сбоя и предлагаемое исправление для каждой. Потом одна строка счётчиков: найдено, подтверждено, опровергнуто, по линзам.

Итог:

- есть `High` → **Нужны изменения**;
- только `Medium` или `Low` → **Изменения желательны**;
- ничего → **Находок нет**.

Если это PR и владелец не сказал `local`, опубликуй **одно** ревью GitHub с событием `COMMENT`:

- по одному inline-комментарию на каждую `High` и `Medium` и не больше чем на пять `Low`, на `path` + `line` (side `RIGHT`); находка на строке вне диффа — в тело ревью;
- текст комментария: `**<Серьёзность> · <класс> · решение: <author|owner>** — <суть>`, затем сценарий сбоя, затем исправление;
- тело ревью: итог, счётчики, режим, линзы, модель, список **всех** `Low` (`path:line` и суть) и маркер `<!-- mozhaev-review round=<r> head=<headRefOid> -->`.

Запрос собери JSON-файлом `<scratchpad>/review/pr-<n>-review.json` (`commit_id`, `event`, `body`, `comments[]` с `path`, `line`, `side`, `body`) и отправь: `gh api --method POST repos/<owner>/<repo>/pulls/<n>/reviews --input <файл>`.

## 6. Уборка

Только после публикации (или отчёта): `git worktree remove --force <scratchpad>/review/<id>`, затем `git worktree prune`, затем для PR — `git update-ref -d refs/remotes/review/pr-<n>` и `git update-ref -d refs/remotes/review/<baseRefName>`. Больше ничего не удаляй. Если шаг не удался — остановись и закончи отчёт точной командой для владельца. Файлы внутри scratchpad (JSON ревью, кэши) не мусор — не проси владельца их удалять.

## Раунды

Раунд 1 смотрит всё изменение. С раунда 2 перечисли все находки ниже `High` под заголовком «Отложено», чтобы автор мог перенести их в описание PR.

## Как линзы становятся острее

Когда владелец, CI или кто-то ещё находит дефект, который скилл пропустил, допиши одну строку в «Замечено в этом репозитории» подходящей линзы: что это было и как это искать.
