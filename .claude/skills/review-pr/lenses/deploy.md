# Линза: deploy — два хостинга, одна сборка

Одна сборка уезжает в CI на два хостинга: глобальный (Netlify) и российский (S3-совместимое хранилище), с гео-DNS перед ними (`DEPLOY-dual.md`, `CLAUDE.md`, правила 6 и 10). Ошибка здесь не видна в `dist/`: она проявляется как наполовину обновлённый хостинг, сертификат, который не продлился, или страница, открывающаяся только с одной стороны границы.

## Метод

0. **Переключатели хостингов.** Каждый deploy-job включается своей переменной репозитория (`DEPLOY_GLOBAL`, `DEPLOY_RU`); `verify` проверяет только включённые. Job без такого условия упадёт у любого, кто ещё не завёл секреты, — находка.
1. **Одна сборка.** Оба деплоя берут один артефакт `dist` из job `build`. Второй `yarn build` в deploy-job — находка: хостинги могут разойтись.
2. **Порядок выкладки на S3.** Сначала новые хешированные файлы `/_astro/*` (без удаления старых), потом HTML, только потом удаление лишнего. HTML, ссылающийся на ещё не залитые файлы, или удаление до замены HTML — находка `High`.
3. **Прерывание.** `concurrency` с `cancel-in-progress: false`: отменённый посреди последовательных `s3 sync` деплой оставляет хостинг наполовину обновлённым.
4. **Кэш.** `/_astro/*` — `immutable` на год на обоих хостингах; HTML — без долгого кэша (`max-age=0, must-revalidate`). Расхождение между `netlify.toml` и заголовками S3 — находка.
5. **Адреса на обоих хостингах.** Папочная структура (`build.format: 'directory'`) и `trailingSlash: 'always'` одинаково понятны Netlify и S3; `404.html` назначен страницей ошибки на S3. Редирект, заданный только в `netlify.toml` или `_redirects`, на S3 не сработает — находка.
6. **Секреты и права.** Секреты только из `secrets.*`; `permissions` у workflow минимальные; нет `pull_request_target` с кодом PR; сторонние actions — по тегу мажорной версии или SHA. В `.env.example` — имена без значений.
7. **Проверка после деплоя.** Шаг `verify` стучится в оба origin напрямую. Он идёт с зарубежных адресов раннера и **не видит** российских блокировок — заявлять «проверено из РФ» на его основании нельзя.
8. **DNS и сертификаты.** При гео-DNS сертификат российского origin выпускается через DNS-01: HTTP-проверка валидатора может уйти на другой origin. Изменение DNS без записи в ADR — находка `Medium`.
9. **Ручной деплой.** Ничто не предлагает деплоить из сессии агента или руками в обход CI.

## Вопросы

1. Что увидит посетитель, если деплой упадёт между двумя шагами `s3 sync`?
2. Откроется ли старая страница, у которой HTML ещё ссылается на прошлые файлы `/_astro/`?
3. Как продлится сертификат российского origin, если валидатор Let's Encrypt придёт с другой стороны гео-DNS?
4. Совпадают ли заголовки кэша на двух хостингах?

## Замечено в этом репозитории

- IP-адреса Netlify фильтруются частью российских провайдеров: HTML доходил, запрос за `/_astro/*.css` обрывался — страница без стилей. Отсюда `inlineStylesheets: 'always'`, но это лечит симптом, а не доступность хостинга.
- Первая версия workflow отменяла запущенный деплой (`cancel-in-progress: true`) — между `s3 sync` это оставляло российский хостинг наполовину обновлённым.
- `setup-node` с yarn 4 через `packageManager`: нужны `corepack enable` и `yarn install --immutable`, глобальный yarn 1 с раннера падает.
- У владельца `node_modules` собраны под macOS: сборка в его папке из Linux-окружения падает на нативном модуле rollup — не повод «чинить» зависимости в репозитории.
- У workflow не было блока `permissions` — `GITHUB_TOKEN` получал права по умолчанию; с 13.10.2026 стоит `contents: read`. Новый job, которому нужно больше, — находка, если это не обосновано.
- Открыто: нет `.env.example`, а workflow ждёт девять секретов — их список есть только в `DEPLOY-dual.md`.
