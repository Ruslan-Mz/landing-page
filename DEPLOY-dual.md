# Двойной хостинг: глобальный + российский

Причина: IP-адреса Netlify фильтруются провайдерами в РФ. Симптом, который
уже наблюдался, — HTML доходит, а запрос за CSS обрывается, и страница
выглядит сломанной. Целевая аудитория `/dev` — как раз РФ.

Схема:

```
                    ┌─ запрос из РФ ────→ российский хостинг (origin RU)
mozhaev.pro ─ GeoDNS┤
                    └─ остальной мир ───→ Netlify (origin GLOBAL)
```

Одна сборка уезжает на оба origin'а через GitHub Actions, поэтому расхождений
между ними быть не может.

---

## 0. Этап 1 — Yandex Object Storage как основной хостинг для всех

GeoDNS требует переноса зоны и времени на проверку. Быстрее и без риска для
почты: сначала перевести `mozhaev.pro` целиком на российский origin. Yandex
Cloud доступен и из ЕС, так что сайт открывается везде. Netlify остаётся
запасной копией; GeoDNS (§3) — этап 2.

DNS остаётся в Namecheap: корень домена указывается записью `ALIAS`
(аналог ANAME), MX и прочие записи не трогаются.

1. **Namecheap → Advanced DNS:** TTL записей `@` и `www` → 5 min. Сразу, до
   всего остального: старый TTL (30 мин) должен истечь к моменту переключения.
2. **Yandex Cloud:** платёжный аккаунт в статусе `ACTIVE`/`TRIAL_ACTIVE`.
3. **Бакет `mozhaev.pro`** (имя = домену, иначе свой домен не привяжется):
   чтение объектов — «Для всех»; Настройки → Веб-сайт → Хостинг,
   главная `index.html`, ошибка `404.html`.
4. **Сервисный аккаунт** `site-deploy`, роль `storage.editor` на каталог →
   «Создать статический ключ доступа». Секрет показывается один раз.
5. **GitHub → Settings → Secrets and variables → Actions:**
   секреты `RU_S3_KEY_ID`, `RU_S3_SECRET`, `RU_S3_BUCKET=mozhaev.pro`,
   `RU_S3_ENDPOINT=https://storage.yandexcloud.net`,
   `RU_ORIGIN_URL=http://mozhaev.pro.website.yandexcloud.net/`;
   переменная `DEPLOY_RU=true`. Затем push (или Run workflow).
   `RU_ORIGIN_URL` — по http: у бакета с точками в имени нет валидного
   сертификата на `*.website.yandexcloud.net`.
6. **Проверка до переключения DNS:** `http://mozhaev.pro.website.yandexcloud.net/`
   открывается со стилями и шрифтами, `/dev/`, `/ru/`, `/dev/ru/`, `/nope/` → 404.
7. **Certificate Manager → Let's Encrypt** на `mozhaev.pro` и `www.mozhaev.pro`,
   проверка через DNS. Запись `_acme-challenge` (CNAME), которую покажет
   консоль, добавить в Namecheap (поле Host — без домена). Дождаться статуса
   `Issued` (обычно минуты).
8. **Бакет → Безопасность → HTTPS:** источник — Certificate Manager, выбрать
   сертификат. Применяется до ~30 минут.
9. **Переключение (Namecheap):** удалить `A @ 75.2.60.5` (Netlify), добавить
   `ALIAS @ → mozhaev.pro.website.yandexcloud.net`, TTL 5 min.
10. **www:** второй бакет `www.mozhaev.pro`, Веб-сайт → «Переадресация» на
    `mozhaev.pro` по https; HTTPS — тот же сертификат;
    `CNAME www → www.mozhaev.pro.website.yandexcloud.net`.
11. **Проверка:** из РФ без VPN (мобильный интернет и домашний провайдер),
    из ЕС; `curl -I https://mozhaev.pro/` — сертификат Let's Encrypt, 200.

Откат: вернуть `A @ 75.2.60.5` — Netlify-копия не удалялась.

Чего нет на этом этапе: сжатия (Object Storage не делает gzip/brotli — для
страниц в десятки килобайт это некритично) и заголовков из `_headers`
(Netlify-специфичный файл, в бакет не выгружается). Оба вопроса закрывает
Yandex CDN поверх бакета — в этапе 2.

## 1. Российский origin

Статику можно положить куда угодно, где есть S3-совместимое хранилище или
обычный веб-сервер. Готовый workflow настроен под S3-совместимый вариант:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Yandex Object Storage + CDN | оплата по факту (копейки), S3 API, сертификат через Certificate Manager | нужен аккаунт Yandex Cloud с биллингом |
| Timeweb Cloud (S3 или статика) | простая панель, поддержка на русском | фиксированный тариф |
| Selectel Object Storage | S3 API, зрелая платформа | тариф выше начального уровня |
| VPS + nginx | полный контроль | нужно самому обновлять и следить |

Что понадобится от выбранного хранилища: включённый режим хостинга статики,
`index.html` как индексный документ, `404.html` как страница ошибки,
публичный доступ на чтение.

## 2. Сертификат — здесь главная ловушка

Домен один, а origin'а два, и **каждому нужен свой валидный сертификат** для
`mozhaev.pro`.

Netlify выпускает его сам через Let's Encrypt, проверяя владение по HTTP.
Но при geo-разделении запрос валидатора может уйти на другой origin, и
проверка провалится. Поэтому на российской стороне **выпускай сертификат с
проверкой через DNS (DNS-01)**, а не через HTTP — она не зависит от того,
куда geo-DNS направит конкретный запрос.

## 3. GeoDNS

Домен зарегистрирован в Namecheap, но обслуживание зоны нужно передать
провайдеру с гео-маршрутизацией — у Namecheap её нет.

| Провайдер | Гео | Цена | Заметка |
|---|---|---|---|
| Gcore DNS | есть | бесплатный тариф | заявлены GeoDNS и failover-проверки |
| ClouDNS | есть | платные тарифы GeoDNS | недорого, зрелый сервис |
| Cloudflare | через Load Balancing | платно | сам Cloudflare нестабилен в РФ |

Порядок: завести зону у выбранного провайдера, перенести все текущие записи
(включая почтовые, если они есть), в Namecheap заменить NS на выданные,
затем настроить правила:

- правило для России (и, при желании, соседних стран) → адрес российского origin;
- правило по умолчанию → адрес Netlify;
- TTL 300 секунд, чтобы переключение применялось быстро;
- failover-проверка, если провайдер её умеет: origin упал — трафик уходит на второй.

Точность геоопределения зависит от поддержки ECS: без неё DNS видит адрес
резолвера, а не пользователя. Человек с публичным DNS (8.8.8.8) может
получить «не свой» origin — при двух рабочих копиях сайта это не страшно.

## 4. Автодеплой

**Каждый хостинг включается отдельно** — переменной репозитория
(Settings → Secrets and variables → Actions → **Variables**):

| Переменная | Что включает |
|---|---|
| `DEPLOY_GLOBAL=true` | выкладку на Netlify и его проверку в `verify` |
| `DEPLOY_RU=true` | выкладку в российский бакет и его проверку в `verify` |

Пока переменной нет, соответствующий job пропускается, а workflow остаётся
проверкой сборки. Включать — только когда у хостинга заведены все секреты.

`.github/workflows/deploy.yml` уже в репозитории. Секреты в настройках
репозитория (Settings → Secrets and variables → Actions):

| Секрет | Что это |
|---|---|
| `NETLIFY_AUTH_TOKEN` | персональный токен Netlify |
| `NETLIFY_SITE_ID` | ID сайта в Netlify |
| `RU_S3_KEY_ID`, `RU_S3_SECRET` | ключи доступа к хранилищу |
| `RU_S3_BUCKET` | имя бакета |
| `RU_S3_ENDPOINT` | напр. `https://storage.yandexcloud.net` |
| `GLOBAL_ORIGIN_URL`, `RU_ORIGIN_URL` | прямые адреса origin'ов для проверки |

Проверочный шаг в конце обращается к каждому включённому origin'у напрямую
и падает, если хоть один отдаёт не ту страницу. Он идёт с серверов GitHub за
пределами РФ, поэтому доказывает, что origin'ы работают, но не что они
доступны из России — для этого нужен мониторинг изнутри (§5).

## 5. Мониторинг

Прямая проверка из GitHub Actions идёт с зарубежных адресов, поэтому она
**не увидит** проблем именно из РФ. Для этого нужен внешний мониторинг с
российскими точками проверки (например, ping-admin.ru) — заведи проверку
`mozhaev.pro` с российских узлов и уведомления на почту.

## 6. Порядок переезда без простоя

1. Поднять российский origin, залить сборку, проверить по прямому адресу.
2. Выпустить сертификат (DNS-01).
3. Перенести зону к geo-провайдеру, **сохранив прежние записи** — сайт при этом
   продолжает работать через Netlify.
4. Убедиться, что зона отвечает корректно, и только потом добавить гео-правило.
5. Проверить из РФ без VPN и из ЕС.
